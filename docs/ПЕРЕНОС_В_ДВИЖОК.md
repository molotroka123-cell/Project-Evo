# ФРОНТИР — перенос в игровой движок

Документ для того, кто будет переписывать игру на другом движке (Unity/C#,
Godot/C#, Bevy/Rust — что угодно). Пишу его прямо, без рекламы: половина текста
про то, чего делать НЕ надо и что сломается молча.

---

## 1. Что мы переносим на самом деле

Обычное представление — «перенести игру на Unity, чтобы улучшить графику».
Числа говорят другое.

| Слой | Строк | Что это |
|---|---:|---|
| **Ядро** (`app/src/core/`) | **23 315** | Правила игры. Ноль обращений к экрану. |
| Рендер (`app/src/render/`) | 14 923 | Рисование на Canvas 2D. |
| Интерфейс (`app/src/ui/`) | 3 340 | Панели, вкладки, модалки. |
| Тесты (`app/tests/`) | 9 325 | 919 проверок в 28 наборах. |

Графика — это 14 923 строки, и они выбрасываются в любом случае: на новом
движке рисуют иначе. А переписывать придётся **23 315 строк ядра**, которые к
графике отношения не имеют вообще.

**Вывод, который надо принять до начала работы: это не порт графики, а
повторная реализация игры.** Ядро на C# — это не перевод, а написание заново по
спецификации, потому что переводить нечего: там нет ни одного вызова к экрану,
только правила.

### Что переносится дословно

Ничего. C# и JavaScript расходятся ровно в тех местах, которые нам важны:
целочисленная арифметика, поведение `Number`, порядок обхода объектов. Об этом
целиком раздел 3.

### Что переносится по смыслу

Вся архитектура. Она к этому и готовилась:

```
ядро (правила) ──отчёты──> слой подключения ──> рисование
     ▲                                              │
     └────────────── НЕТ обратной связи ────────────┘
```

Ядро не знает про экран. Рендер не меняет состояние. Между ними — один файл
`integrate.js`, где отчёты модулей превращаются в изменения мира. На новом
движке эта схема остаётся; меняется только правая часть.

## 2. Что сломается, если делать наивно

### 2.1 Детерминизм — главное

Во всём ядре **нет ни одного `Math.random`**. Вся случайность идёт через
`sim.rng` от сида, и за этим следит отдельная проверка в каждом тесте модуля.
Это не гигиена ради гигиены — на этом построены три вещи:

* **сохранения** — состояние ГПСЧ пишется в файл и восстанавливается;
* **«тень прошлой партии»** — сравнение двух прогонов на одном сиде, слепок в
  слепок;
* **воспроизведение багов** — сид в адресе страницы задаёт мир целиком.

Если в C#-версии генератор даст хоть одно другое число, разойдётся ВСЁ: карта,
соседи, погоды. Проверить это глазами невозможно — расхождение выглядит как
«просто другой мир».

### 2.2 Ловушка `Math.imul`

Генератор — mulberry32:

```js
export function createRng(seed) {
  let a = seed >>> 0;
  const next = function () {
    a |= 0; a = (a + 0x6D2B79F5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
  ...
}
```

Три места, где C# по умолчанию сделает НЕ то:

1. **`Math.imul`** — 32-битное знаковое умножение с отбрасыванием переполнения.
   В C# обычный `*` на `int` в блоке `checked` бросит исключение, а вне его даст
   верный результат только если тип точно `int`. Нужен `unchecked((int)(a * b))`.
2. **`>>>`** — беззнаковый сдвиг. В C# это `>>` на `uint`, а не на `int`.
   На `int` знаковый сдвиг даст другое число для отрицательных.
3. **`| 0`** — приведение к int32. В C# просто держите переменную `int`.

Правильный порт:

```csharp
public sealed class Rng {
    private uint a;
    public Rng(uint seed) { a = seed; }

    public double Next() {
        unchecked {
            a = a + 0x6D2B79F5u;
            uint t = (uint)((int)(a ^ (a >> 15)) * (int)(1u | a));
            t = (t + (uint)((int)(t ^ (t >> 7)) * (int)(61u | t))) ^ t;
            return ((t ^ (t >> 14))) / 4294967296.0;
        }
    }
    public uint GetState() => a;
    public void SetState(uint s) { a = s; }
}
```

### 2.3 Контрольные значения — сверяйте до того, как писать дальше

Первое, что должен сделать порт, — совпасть с этими числами. Не совпал —
дальше идти бессмысленно, потому что мир будет другой.

**seed = 4242, восемь вызовов `next()` подряд:**

```
[0] 0.54670613352209330
[1] 0.27860878920182586
[2] 0.93123691715300083
[3] 0.50722246640361845
[4] 0.66877828026190400
[5] 0.28787897294387221
[6] 0.25968898204155266
[7] 0.40142279746942222
состояние после восьми вызовов: 1767628858
```

**seed = 1, четыре вызова:**

```
[0] 0.62707394058816135
[1] 0.00273572118021548
[2] 0.52744703995995224
[3] 0.98105096747167408
```

**Шум fBm (4 октавы), генератор от seed 4242:**

```
fbm(0, 0)          =  0.00000000000000000
fbm(1.5, 2.5)      = -0.28283999999999998
fbm(10.25, -3.75)  = -0.20623749999999999
```

Шум зависит от таблицы перестановок, которую тасует тот же генератор
(алгоритм Фишера—Йетса сверху вниз, `for (i = 255; i > 0; i--)`). Порядок
тасования менять нельзя — числа разойдутся.

### 2.4 Порядок обхода — тихий убийца

В JS `Object.keys()` и `for...in` возвращают ключи в порядке вставки (для
строковых ключей). Ядро на это опирается: например, мастера промыслов
назначаются «первым по списку», сословия обходятся в фиксированном порядке.

В C# `Dictionary<K,V>` порядок обхода **не гарантирует**. Берите
`List<KeyValuePair<>>`, `SortedDictionary` или явный массив ключей. Иначе
партия будет расходиться сама с собой между запусками — на одном и том же сиде.

### 2.5 Числа с плавающей точкой

В JS все числа — `double`. Если в C# где-то окажется `float`, накопленная
разница за тысячу игровых дней превратится в другую партию. Держите `double`
везде в ядре. `float` допустим только в графике.

## 4. Контракт связей — соблюдать обязательно

Каждый `link_*` устроен одинаково, и это не стиль, а требование:

```js
export function xxxLinks(sim) {
  return {
    mods:    { stability: -0.4, happy: -2, estates: {...} },  // что изменить
    reasons: { stability: [{ ru: 'Народ помнит голод', v: -0.4 }] },  // почему, словами
    events:  [{ text: '📜 ...', type: 'warn' }],              // что сказать игроку
    flags:   { memory: {...} },                               // новое состояние памяти
  };
}
```

Четыре правила, каждое куплено ошибкой:

1. **Модуль ничего не мутирует.** Применяет отчёт только `integrate.js`. Иначе
   модуль нельзя протестировать в одиночку.
2. **У каждой петли обратной связи есть потолок и выход.** Спираль без выхода —
   это партия, которую нельзя спасти, и игрок бросает игру.
3. **Каждая поправка объяснена словами** в `reasons`. Игрок обязан прочитать
   причину, а не гадать, почему у него падает порядок.
4. **Память хранит СОБЫТИЯ, а не СОСТОЯНИЯ.** Мы на этом обожглись: мор
   записывался заново каждые сутки, пока лежали больные, и память намертво
   стояла на потолке двенадцать лет вместо того, чтобы таять.

## 5. Что потеряется при переходе на Unity

Говорю прямо, потому что решение принимать не мне.

* **Игра перестанет открываться двойным кликом.** Сейчас это один файл
  `frontier.html` на 2.6 МБ, работающий офлайн без установки.
* **Пропадёт ссылка на телефон.** Unity WebGL — десятки мегабайт, не работает
  из `file://`, и мобильный Safari его худшая платформа. Десктопный билд — это
  отдельные бинарники под Windows и Mac.
* **919 проверок придётся написать заново.** Они на JS и проверяют JS-код.
* **Появится зависимость от лицензии и редактора.** Сейчас сборка — один
  `node tools/build.mjs` без внешних сервисов.

### Что взамен

* Настоящий конвейер ассетов: модели, материалы, анимации, префабы.
* Освещение, тени, постобработка из коробки, без ручной реализации.
* Редактор сцены — расстановка и настройка мышью, а не числами в коде.
* Физика, партиклы, звук как готовые подсистемы.

### Третий путь, который уже проверен

В репозитории лежит `app/src/render3d/scene3d.js` — трёхмерная сцена на
Three.js, работающая **на живых данных этой игры**: 40 построек, 42 жителя,
настоящая геометрия, солнце с теневой картой, туман. Она уже даёт буфер
глубины, GPU-освещение и реальные тени — то есть тот самый порог графики, ради
которого затевается переход, — и при этом сохраняет и офлайновый один файл, и
ссылку на телефон, и все 919 проверок.

Скриншоты: `shots/d3_low.png`, `shots/d3_wide.png`, `shots/d3_eve.png`.

Чего в ней пока нет: выбора постройки мышью (нужен raycast), воды с берегом,
растительности, и модели зданий — коробки с крышами вместо glTF.

## 6. Порядок работ, если решение принято

1. **`rng.js` → C#.** Сверить с контрольными значениями из раздела 2.3.
   Не сошлось — остановиться и чинить, дальше идти нельзя.
2. **`data.js`.** Голые таблицы, ни одной формулы. Механическая работа.
3. **`world.js` + `worldgen2.js`.** Карта. После этого можно нарисовать первый
   кадр и увидеть, что мир совпал с оригиналом.
4. **`simulation.js`.** Главный цикл. Самый большой и самый связный файл.
5. **Системы** по одной, каждая со своим набором тестов, портированным следом.
6. **Связи** `link_*` — последними, потому что они читают всё остальное.
7. **Графика** — только теперь. До этого момента она не нужна: правильность
   проверяется тестами, а не глазами.

Пункты 1–6 — это работа, не зависящая от движка вообще. Она одинакова для
Unity, Godot и чего угодно ещё.

## 7. Как проверять, что перенос верен

Не «выглядит правильно», а числом:

```
Прогнать оригинал и порт на одном сиде N дней без действий игрока
и сравнить слепки: население, казна, порядок, эпоха, постройки, технологии.
Расхождение хоть в одном числе на любом дне = ошибка переноса.
```

Инструмент для снятия слепков уже есть — `link_ghost.js`, он именно этим и
занимается: `snapshotOf(sim)` возвращает плоский объект из чисел. Выгрузите
слепки оригинала в JSON и сверяйте с портом.

Это единственный честный способ. Всё остальное — «вроде похоже».
