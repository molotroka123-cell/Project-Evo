Все числа получены замером, не оценкой. Метод замера описан в §1, чтобы любой
мог повторить и оспорить.

Смежное: `docs/graphics-audit.md` §7 (те же замеры в контексте проблем),

## 1. Как замерялось

### Стенд
```
Chromium /opt/pw-browsers/chromium
--enable-gpu --use-gl=swiftshader     ← ПРОГРАММНАЯ растеризация
```

**Это важно понимать.** SwiftShader считает всё на CPU. Абсолютные числа
пессимистичны относительно машины с настоящей видеокартой — примерно в 2–4 раза.
**Соотношения между пресетами и зумами достоверны в любом случае.**

Практическое правило чтения: считайте эти числа поведением игры на **слабом
ноутбуке с интегрированным видео 5-летней давности**. Если игра укладывается
здесь, она укладывается везде.

### Сцена
```
55 построек, 226 жителей, 28 животных
мир 96×96 тайлов, эпоха 8, полдень, ясно
симуляция на паузе (чтобы кадры сравнивались друг с другом)
```

### Почему нельзя мерить FPS счётчиком rAF
`npm run shot` печатает `FPS≈61` для любого пресета, включая тот, что на самом
деле выдаёт 26 кадров. Причина: rAF упирается в vsync, и счётчик всегда
показывает 60. **Этой цифре нельзя верить.**

Использовано два честных метода:

**Метод А — время одного кадра со сбросом конвейера.**
```js
const a = performance.now();
renderer.draw(sim, 0.016);
ctx.getImageData(0, 0, 1, 1);   // ← заставляет дождаться растеризации
t.push(performance.now() - a);
```
Без `getImageData` Canvas 2D возвращает время постановки команд в очередь
(0,7–1,6 мс), а не время рисования. Разница с реальностью — в 20 раз.

**Метод Б — живой цикл без вертикальной синхронизации.**
```
chromium --disable-gpu-vsync --disable-frame-rate-limit
```
Считаются настоящие кадры за 3 секунды с работающей игрой, HUD и симуляцией.

Скрипты замера лежали во временной папке и в репозиторий не добавлялись —
воспроизводятся по описанию выше за 15 минут.

## 3. Замеренное: память

Все кэши — offscreen-канвасы, то есть текстуры. Считаются как `w × h × 4 байта`.

### 3.1 На замеренной сцене (55 зданий, 226 жителей)

| Кэш | eco | medium | high | ultra |
|---|---|---|---|---|
| Спрайты зданий, 54 записи | 3,0 МБ | 8,8 МБ | 16,7 МБ | 16,7 МБ |
| Чанки местности, zoom 1,6 (4 шт.) | 1,0 МБ | 2,3 МБ | 4,0 МБ | 4,0 МБ |
| Чанки местности, zoom 0,5 (24 шт.) | 6,0 МБ | 13,5 МБ | 24,0 МБ | 24,0 МБ |
| Мини-карта `terrain.low` | 0,14 МБ | 0,14 МБ | 0,14 МБ | 0,14 МБ |
| Основной холст 1600×900 | 5,5 МБ | 5,5 МБ | 5,5 МБ | 5,5 МБ |
| Вспомогательные (свечение, облако, блик, лучи, виньетка, зерно) | ~0,1 МБ | ~0,3 МБ | ~6 МБ | ~6 МБ |
| **Итого сейчас** | **~10 МБ** | **~22 МБ** | **~40 МБ** | **~40 МБ** |

`_rays` и `_vig` печатаются в полный размер окна — 1600×900×4 = 5,5 МБ каждый.
Это они дают +6 МБ на `high`/`ultra`.

### 3.2 Худший случай — потолки не заданы нигде

| Кэш | Формула | Потолок при `high` |
|---|---|---|
| `SpriteCache.map` | 58 зданий × до 4 ступеней эпохи, ключ `id\|era\|size\|detail` | **~72 МБ** |
| `terrain.chunks` | мир 96×96 = 36 чанков × (16·32)² × 4 | **36 МБ** |
| `PeopleSprites.map` | 10 эпох × 9 профессий × 3 внешности = 270 листов | **~35 МБ** |
| **Итого худший случай** | | **~150 МБ** |

**Ни один из трёх кэшей не имеет ни потолка, ни вытеснения.**
`SpriteCache` и `PeopleSprites` очищаются только при смене пресета качества.
`terrain.chunks` — при смене сезона, качества или сида мира.

Игрок, прошедший все 10 эпох за одну сессию, накопит все спрайты всех эпох —
и они останутся в памяти навсегда, включая спрайты зданий, которых уже нет.

`high` в бюджет укладывается. Проблемы — в `ultra` (§5.4) и на дальнем зуме (§5.3).

### 5.3 Бюджет по зумам — **сейчас нарушен**

| Зум | Бюджет `high` | Сейчас | Статус |
|---|---|---|---|
| 0,5 (карта) | ≤ 8 мс | **24,3 мс** | **×3 сверх бюджета** |
| 1,0 | ≤ 14 мс | 21,6 мс | ×1,5 сверх |
| 1,6 (основной) | ≤ 16,6 мс | 11,0 мс | ✓ |
| 3,0 (близко) | ≤ 16,6 мс | 12,8 мс | ✓ |

**Дальний зум должен быть самым дешёвым, а он самый дорогой.** Причина: чанков
24 вместо 4, каждый 512×512, блитятся с уменьшением, LOD нет, жители рисуются
все 226 при размере 7 px. Лечится работой 4.1–4.2 из дорожной карты (3,5 дня).

### 5.4 Что делать с `ultra`

`ultra` минус `high` = 12,5 мс на zoom 1,6. Вся разница — в двух параметрах:

| Параметр | high | ultra | Цена |
|---|---|---|---|
| `grain` | 0 | 0,030 | **~8 мс** — полноэкранная заливка паттерном в режиме `overlay` каждый кадр |
| `bloomDiv` | 6 | 4 | ~4,5 мс — больше и ярче ореолов свечения |

Зерно 3 % прозрачности стоит половину бюджета кадра. Два решения:
- **дёшево:** обновлять зерно раз в 3 кадра (уже частично: `grainAge % 12`,
  но `fillRect` всё равно каждый кадр) → экономия ~5 мс;
- **правильно:** зерно как CSS-слой поверх канваса, композитится браузером на
  GPU → экономия все 8 мс, ноль работы в кадре.

### 6.3 Три обязательные правки в `quality.js`

**1. `ultra` не должен раздаваться автоматически.**
```js
// quality.js, функция guessQuality()
if (mem >= 8 && cores >= 8) return 'ultra';
```
Замер: 26,3 FPS. `ultra` — ручной выбор для тех, кто готов, а не подарок
каждому десктопу. Заменить на `'high'`.

**2. Два разных «авто».**
Конструктор `Renderer` берёт `guessQuality()`.
`Renderer.setQuality('auto')` стартует с жёстко зашитого `'high'`.
Телефон, выбравший «авто» из будущего меню графики, получит `high` — 41,4 мс.
Должно быть `guessQuality()` в обоих местах.

**3. Ограничение dpr — по площади, а не по числу.**
```js
// конструктор Renderer
this.dpr = Math.min(2, window.devicePixelRatio || 1);
```
На телефоне 412×915 с dpr 3 холст станет 1236×2745 = 3,4 млн пикселей.
Правило должно быть: `dpr` подбирается так, чтобы площадь холста не превышала
**2,5 млн пикселей** на `medium` и **4,5 млн** на `high`.

### 6.4 Авто-тюнер: что с ним не так

`quality.js:makeAutoTuner` наблюдает 10 секунд, считает долю кадров медленнее
1/40 с, и при доле > 0,35 снижает пресет на ступень. Три недостатка:

1. **Работает только вниз.** Игрок, начавший на `eco` из-за фоновой нагрузки,
   останется на `eco` навсегда.
2. **Срабатывает один раз** (`done = true`). Город из 20 зданий и город из 200 —
   разная нагрузка, а тюнер уже отработал на первой минуте.
3. **Не знает про зум.** Замер: `high` на zoom 1,6 — 11,0 мс, на zoom 0,5 —
   24,3 мс. Тюнер, откалиброванный на одном зуме, ошибается на другом.

Что должно быть: скользящее окно 5 с, работа в обе стороны, гистерезис
(снижать при p95 > 22 мс, повышать при p95 < 11 мс в течение 20 с),
пауза калибровки при активной панораме и зуме.

## 7. Регламент контроля

### 7.1 После каждой графической правки
```bash
npm run build && npm run shot
```
- `=== КОНСОЛЬ ЧИСТАЯ ===` — обязательно;
- «нет файлов арта: N» не выросло;
- посмотреть глазами `shots/town.png`, `shots/people.png`, `shots/map_far.png`.

### 7.2 Раз в неделю — полный замер
Методы А и Б из §1 по всем четырём пресетам и четырём зумам.
Записывать в таблицу с датой. Регресс определяется как:
- рост p50 более чем на 10 % на любом пресете;
- рост p95 более чем на 15 %;
- рост памяти кэшей более чем на 10 %;
- рост `frontier.html` более чем на 5 %.

### 7.3 Что мерить обязательно при добавлении новой фичи
| Фича | Что померить до и после |
|---|---|
| Новый спрайт или архетип | размер `SpriteCache` в МБ |
| Новый слой отрисовки | p50 и p95 кадра на всех четырёх зумах |
| Новый пост-эффект | разница `high` минус `high` без эффекта |
| Новые сущности на карте | p50 при 2× их числе |
| Новый ассет | вес `frontier.html` |

### 7.4 Три числа, которые надо помнить наизусть
- **16,6 мс** — бюджет кадра. Всё остальное — детали.
- **11,0 мс** — где сейчас `high` на основном зуме. Запас 5,6 мс, и его надо беречь.
- **24,3 мс** — где сейчас `high` на дальнем зуме. Это долг, и его надо отдать.
