# ФРОНТИР — реестр ассетов и конвейер арта

Как ассет попадает в игру: откуда берётся, как называется, где лежит, кто его
грузит, что происходит, если его нет.

Смежное: `docs/graphics-audit.md` §4 (что есть и чего нет),
`docs/art-direction.md` §10 (чек-лист приёмки).

Из этого следуют два правила, действующие **всегда**, а не только сейчас:

> **Правило 1. Отсутствие ассета — не ошибка.** Игра обязана работать и
> выглядеть прилично при нуле нарисованных файлов. Механизм отката на
> процедурный спрайт (`artpack.js:building()` → `null` → `sprites.js`) —
> это архитектура, а не заглушка. Не убирать.

> **Правило 2. Просить можно только то, что есть.** Каждый запрос
> несуществующего файла — красная 404 в консоли, а приёмка требует нуля.
> Список запрашиваемого собирается **по факту наличия файлов на диске**
> (`tools/build.mjs:refreshArtList` → `artpack_list.js`), а не вручную.

## 1. Правила именования

### 1.1 Формула

```
<категория>_<стабильный_id>[__<вариация>][@<эпоха>].png
```

- **категория** — из закрытого списка §2. Строчные латинские буквы.
- **стабильный_id** — **точно тот же идентификатор, что в коде.**
  Для зданий — ключ из `data.js:BUILDINGS`. Для фракций — `id` из
  `data.js:FACTIONS`. Для юнитов — `id` из `data.js:UNITS`.
  Это единственный способ не завести отдельную таблицу соответствий.
- **вариация** — необязательная, через двойное подчёркивание: `__a`, `__b`,
  `__winter`, `__ruined`. Нужна там, где один объект имеет несколько обликов.
- **эпоха** — необязательная, через `@`: `@0`…`@9`. Только там, где объект
  реально меняется по эпохам и нарисован отдельно.

### 1.2 Примеры

```
buildings_hut.png                  хижина, один облик
buildings_castle.png               замок
buildings_farm__winter.png         поле зимой
factions_wolves_capital.png        столица Волчьего Предела
factions_wolves_emblem.png         эмблема Волчьего Предела
units_knight.png                   рыцарь
res_food.png                       иконка еды
spire_stage_3.png                  Шпиль, стадия 4 (нумерация с нуля)
props_fence@4.png                  забор средневековья
```

### 1.3 Что запрещено
- Пробелы, кириллица, заглавные буквы, дефисы в имени файла.
- Имена вида `hf_20260730_180356_26f5cf48-….png` — то, что отдаёт генератор.
  Такие имена живут только в `art/raw/` и в `tools/art/raw_map.tsv`,
  в `app/assets/` они не попадают никогда.
- Порядковые номера (`building_01.png`). Порядок меняется, id — нет.
- Разные имена для одного объекта в разных местах. Один объект — один id.

### 1.4 Технические требования к файлу

| Параметр | Значение | Почему |
|---|---|---|
| Формат | PNG-32 с альфой | нужна прозрачность и мягкая кайма |
| Большая сторона | **≤ 512 px** | здание на экране максимум 150 px (zoom 3, `size 2`); больше — трата памяти и веса |
| Иконки ресурсов | 128×128 | HUD, ретина |
| Эмблемы фракций | 256×256 | модалка дипломатии |
| Заставки эпох | 1920×1080 | полноэкранные |
| Обрезка | по границам непрозрачного | делает `cutout.mjs` автоматически |
| Точка привязки | **низ-центр** | здание стоит на земле: `dy = sy + size - dh` в `drawBuilding` |
| Тень | **запечена в спрайт**, контактная, у основания | так уже сделано в промтах: «small dark contact shadow hugging the base» |
| Свет | сверху-слева под 45° | канон проекта, см. `art-direction.md` §5.1 |
| Вес одного файла | ≤ 80 КБ после сжатия | 58 зданий × 80 КБ = 4,6 МБ; больше — билд неподъёмен |

**Про вес — важно.** Сейчас `frontier.html` весит 1,68 МБ, из которых 1,31 МБ —
три медиафайла в base64. Спрайты **не инлайнятся** сборщиком: `build.mjs`
вшивает только JS. Значит, у игры два разных механизма доставки ассетов:

| Механизм | Кто им пользуется | Работает из `file://` | Вес |
|---|---|---|---|
| base64 внутри бандла (`ui/assets.js`) | обложка, победа, музыка | **да** | +33 % к исходнику |
| внешние файлы рядом (`assets/sprites/`) | спрайты зданий | **только если папка лежит рядом с HTML** | как есть |

Это надо решить сознательно (см. §6), а не оставлять как есть.

## 2. Реестр ассетов

Схема записи реестра — то, что должно быть у каждого ассета:

```
id            стабильный идентификатор, совпадает с id в коде
path          путь относительно app/assets/
category      одна из 11 категорий ниже
faction       id фракции или null (общий для всех)
era           номер эпохи 0–9 или null (не зависит от эпохи)
variant       вариация или null
fallback      что рисуется, если файла нет
priority      очередь загрузки: 0 сразу, 1 после первого кадра, 2 лениво
```

| `factions_emblem` | `ui/factions_<fid>_emblem.png` | 8 | да | нет | цветной кружок `⬤` | 2 |

### 2.3 Юниты: особый случай

7 записей (`militia` `swordsman` `knight` `musketeer` `marksman` `soldier`
`drone`) помечены в каталоге промтов `priority: 0` с причиной:
**«renderer.js не рисует бойцов вообще — армия это число во вкладке»**.

Правило: **не заказывать арт под то, чего нет в рендере.** Сначала код рисует
объект с процедурной заглушкой, потом под него заказывается арт. Обратный
порядок даёт то, что произошло с 42 зданиями: файлы генерируются, ложатся
неизвестно куда и не доезжают.

Та же логика у 4 погодных подложек, 2 альтернативных обложек, листа достижений
и постера карты мира — все `priority: 0`, все не заказывать.

## 3. Приоритеты загрузки

| Приоритет | Когда грузится | Что | Правило |
|---|---|---|---|
| **0** | до первого кадра | иконки ресурсов, обложка, шрифт | без них интерфейс выглядит сломанным |
| **1** | сразу после первого кадра, параллельно | здания текущей и следующей эпохи, Шпиль | игрок видит их в первую минуту |
| **2** | лениво, по требованию | здания будущих эпох, фракции, животные, реквизит, заставки | до них ещё часы игры |

Сейчас `ArtPack.preload()` грузит **весь** список сразу. При 42 файлах по 80 КБ
это 3,4 МБ параллельных запросов на старте — на телефоне через мобильную сеть
это заметная пауза. Правило на будущее:

```
preload()  — только приоритет 0 и 1 текущей эпохи
request(id) — вызывается из drawBuilding, когда здание впервые попало в кадр
```

Механизм `request(id)` уже есть в `artpack.js` — он просто не используется.

## 4. Конвейер: как арт попадает в игру

### Шаг 1. Промт
Берётся из `tools/art/prompts.json` — 153 готовых промта с полями
`id`, `category`, `file`, `aspect`, `prompt`, `priority`, `why`.
Просмотр в браузере: `tools/art/prompts.html`.

Все промты уже содержат обязательные части:
- ракурс: приподнятый вид три четверти, ~65° от вертикали;
- свет: тёплый дневной сверху-слева под 45°, мягкое AO;
- контактная тень у основания;
- **фон — сплошная магента `#FF00FF`** как хромакей;
- требование поместить объект целиком с запасом по краям.

**Не переписывать промты по частям.** Если нужен новый ассет — добавить запись
в `prompts.json` по образцу соседней, сохранив все технические абзацы.

### Шаг 2. Генерация
Любой генератор, дающий стабильный магентовый фон. Файлы скачиваются **как
есть**, с именами генератора.

### Шаг 3. Раскладка в `art/raw/`
Файл кладётся под именем целевого спрайта: `buildings_hut.png`, а не под
именем генератора. Соответствие «имя генератора → целевое имя» ведётся в
`tools/art/raw_map.tsv` (два столбца, разделитель — табуляция).
Инструкция для человека — `art/raw/ИМЕНА.md`.

### Шаг 4. Вырезание фона
```bash
node tools/art/cutout.mjs [папка-источник] [папка-результат]
# по умолчанию: art/raw → app/assets/sprites
```

Что делает `cutout.mjs` (реализовано, читать `tools/art/cutout.mjs`):
1. **Определяет фон по тону, а не по точному цвету.** Генератор рисует не
   ровный `#FF00FF`, а малиновый градиент. Критерий: насыщенность > 0,25,
   зелёный канал провален относительно красного и синего минимум на 40,
   тон в диапазоне 275°…345°.
2. **Удаляет только пиксели, связанные с краем кадра** (заливка от рамки внутрь).
   Иначе вырезало бы розовые детали внутри самой постройки — черепицу, ткань, флаг.
3. **Смягчает кромку субъекта** полупрозрачной каймой. Без этого по контуру
   остаётся розовая обводка, которая в игре бросается в глаза сразу.
4. **Обрезает по границам непрозрачного** и пишет PNG.
5. **Честно помечает негодные файлы.** Если в кадре нарисованы трава, небо или
   солнце вместо чистого фона — файл в вывод не попадает, а печатается в списке
   «требуют перегенерации». Такие **чинить нельзя**, надо генерировать заново.
6. Переписывает `MANIFEST` в `artpack.js` по списку успешно обработанных.

### Шаг 5. Нормализация — **этого шага сейчас нет, и он обязателен**
`cutout.mjs` не масштабирует. На выходе — то разрешение, которое дал генератор
(обычно 1024–2048 px). Для игры, где здание занимает максимум 150 экранных
пикселей, это в 7–13 раз больше нужного и превращает 58 зданий в десятки
мегабайт.

Что должен делать шаг нормализации:
- ужать до 512 px по большей стороне (для `size: 1`; для `spire` — 768);
- сжать PNG (квантование палитры до 256 цветов даёт 3–5× без видимой потери);
- проверить, что точка привязки — низ-центр, а тень не обрезана;
- отклонить файл, если после сжатия он тяжелее 80 КБ.

### Шаг 6. Сборка
```bash
npm run build
```
`tools/build.mjs:refreshArtList()` читает `app/assets/sprites/`, собирает список
реально существующих `buildings_*.png` и переписывает `artpack_list.js`.
Игра просит только то, что есть. Число нарисованных спрайтов печатается в
итоговой строке сборки.

### Шаг 7. Приёмка
```bash
npm run shot
```
Требования:
- `=== КОНСОЛЬ ЧИСТАЯ ===`;
- строка «нет файлов арта: N» — **N должно быть равно нулю** после публикации;
- визуальная проверка `shots/town.png` и `shots/people.png` по чек-листу
  §10 `art-direction.md`.

## 5. Известная нестыковка конвейера — починить

Два разных генератора пишут два разных списка одного и того же:

| Кто | Что пишет | Источник данных |
|---|---|---|
| `tools/art/cutout.mjs` | `MANIFEST` в `artpack.js` | результат обработки |
| `tools/build.mjs` | `AVAILABLE` в `artpack_list.js` | содержимое папки |

Сейчас они расходятся: `MANIFEST` содержит 42 id, `AVAILABLE` — те же 42,
а на диске ноль файлов. Первый же `npm run build` перепишет `AVAILABLE` в
пустой список, а `MANIFEST` останется с 42 — и документ будет врать.

**Как чинить:** `MANIFEST` остаётся **декларацией намерения** («для этих
зданий планируется арт»), `AVAILABLE` — **фактом** («эти файлы лежат на диске»).
`cutout.mjs` не должен трогать `artpack.js` вообще: его дело — вырезать фон.
Это правка на 15 минут, но без неё через месяц никто не поймёт, какой список
чему соответствует.

## 6. Развилка доставки: инлайн или файлы рядом

Требование «двойной клик по `frontier.html`, работает офлайн» ставит вопрос:
как доставить 42 PNG?

| Вариант | Плюс | Минус |
|---|---|---|
| **A. Всё в base64 внутри HTML** | один файл, гарантированно работает из `file://` | билд вырастет с 1,68 МБ до ~6 МБ; парсинг base64 на старте; замер сейчас: 1,31 МБ base64 уже даёт DCL 661 мс |
| **B. Папка `assets/` рядом с HTML** | билд остаётся лёгким, спрайты грузятся лениво | «двойной клик» превращается в «распакуй архив и не потеряй папку»; часть браузеров ограничивает `file://` |
| **C. Гибрид** | обязательный минимум (иконки, обложка) — инлайн; спрайты — рядом; при их отсутствии откат на процедурные | сложнее объяснить пользователю |

**Рекомендация — C**, и она уже наполовину реализована: механизм отката
работает, `shot.mjs` отдельно считает отсутствующий арт. Осталось:
1. выкинуть `victory.jpg` (313 КБ) и `main_theme.mp3` (353 КБ) из base64 в
   папку рядом — их отсутствие не ломает игру, а вес билда падает вдвое;
2. поставлять две сборки: `frontier.html` (лёгкий, процедурная графика,
   двойной клик) и `frontier_full.zip` (HTML + `assets/`, полный арт).

Замер, обосновывающий это: сейчас **77 % веса игры — три медиафайла**,
которые игрок суммарно видит секунд десять.

## 7. Добавление нового ассета: чек-лист

1. Объект **уже рисуется** в `renderer.js` хотя бы процедурно? Если нет —
   сначала код, потом арт. (Правило из §2.3.)
2. Добавить запись в `tools/art/prompts.json`: `id`, `category`, `file`,
   `aspect`, `prompt` (скопировать технические абзацы у соседа), `priority`, `why`.
3. Сгенерировать. Проверить: фон сплошной магентовый, объект целиком в кадре,
   свет сверху-слева.
4. Положить в `art/raw/` под целевым именем. Дописать строку в `raw_map.tsv`.
5. `node tools/art/cutout.mjs` — убедиться, что файл в списке годных.
6. Нормализовать: ≤ 512 px, ≤ 80 КБ, привязка низ-центр.
7. Проверить по чек-листу §10 `art-direction.md` — все 10 пунктов.
